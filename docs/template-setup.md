# Using this app as a template for a new client

This app started as a single-business site (Jay's Auto Detailing) but is built as a
reusable template — see `docs/project_intent` context in memory, or just ask Kevin.
Treat what's here as the **first template type**: an auto-detailing business with
vehicle-based pricing and scheduling. A future client in a different line of business
will need a different template type; this doc covers what to change to relaunch the
*same* type of business (another detailer) for a new client, and flags what's a bigger
lift if the next client is a genuinely different kind of business.

## 1. Environment variables (`.env`)

All non-secret, per-deployment config lives in the committed `.env` file — real values
are checked in directly (they're not sensitive), so a new deployment just edits them:

| Variable | Used for |
|---|---|
| `PUBLIC_BUSINESS_NAME` | Business name, interpolated into email subjects/bodies and the create-account confirmation message |
| `PUBLIC_BUSINESS_OWNER_PHONE` | Shown in the footer and the appointment confirmation email |
| `BUSINESS_OWNER_EMAIL` | Recipient for new-booking notification emails |
| `EMAIL_FROM_ADDRESS` / `EMAIL_CONFIRMATION_FROM_ADDRESS` | Sending addresses for outgoing email — **need a domain verified with your email provider (Resend/SES) for the new business**, not just an edit here |
| `PUBLIC_BUSINESS_TIMEZONE` | IANA timezone (e.g. `America/Phoenix`) used for all appointment date/time math — see `src/lib/shared/businessTime.ts` |
| `GOOGLE_PLACE_ID` / `GOOGLE_PLACES_API_KEY` | Google Business Profile reviews on `/reviews` |
| `GOOGLE_MAPS_LISTING_URL` | "Leave a review" / "See all reviews" links fall back to this if a Place ID isn't configured |

Secrets that stay empty in the committed `.env` and get resolved from the Amplify
Console at build time (see `scripts/writeRuntimeEnv.js`) — these need to be set in the
Amplify Console (AWS) or Vercel's project settings, not edited in this file:

| Variable | Notes |
|---|---|
| `RESEND_API_KEY` | Email sending (currently used on both platforms — see `email/index.ts`'s TEMPORARY note) |
| `DATABASE_URL` | Postgres/Neon connection string — Vercel platform only |
| `VERCEL_OIDC_TOKEN` | Vercel platform only |
| `SUPPRESS_EMAIL` | Set to `"true"` to silence real sends while testing a new deployment |

AWS-side identity (Cognito User Pool ID/Client ID, AppSync endpoint) comes from
`amplify_outputs.json`, generated by `ampx sandbox` / the deploy pipeline — not something
to hand-edit.

## 2. Homepage copy

`src/lib/content/home.ts` — the one file to edit for the homepage's marketing copy
(`valueProp`, `highlights`, `resultsBlurb`). Pulled into `src/routes/+page.svelte`, which
should not need touching just to reword the homepage.

## 3. Images

`src/lib/assets/images/` — exactly three to replace:
- `hero.svg` — logo, used in the header and passed to the browser tab favicon config
- `background.jpeg` — site background
- `working.jpeg` — homepage hero photo

## 4. Portfolio (`static/portfolio/`)

Not auto-specific — reusable as-is for any business showing before/after or example work.
Convention: sequentially numbered directories starting at `1`, each containing exactly:
- `services.txt` — plain text, one line, shown as the caption
- `video.mp4` — the before/after clip

`src/lib/portfolio.ts`'s `getPortfolio()` autodiscovers these by requesting
`/portfolio/N/services.txt` for `N = 1, 2, 3, ...` and **stops at the first missing
number** — so entries must be contiguous. Deleting entry `2` while `3` still exists would
silently hide `3` too; renumber instead of leaving gaps.

## 5. Vehicle data (`static/vehicle-data/`) — optional module

Fully generic — sourced from NHTSA's public vPIC API (`scripts/buildVehicleData.ts`), not
specific to any one auto business. Only relevant if the new client's business also needs
year/make/model selection (i.e., another vehicle-based business). Regenerate with
`npm run build:vehicle-data` if you need fresher data; omit entirely (and the scheduling
form's vehicle fields with it) for a non-vehicle business.

## 6. Scope limit: `ServiceType` / `VehicleCategory` are schema-level, not config

`ServiceType` (`FULL` / `INTERIOR` / `TREATMENT`) and `VehicleCategory` (`coupe` / `sedan`
/ `van` / `suv` / `jeep` / `truck`) are baked into both the Amplify Data schema
(`amplify/data/resource.ts`) and the Postgres schema (`storage/postgres/schema.sql`), and
`ServicePrice` is priced per-vehicle-category. Fine as-is for another vehicle-detailing
business. A fundamentally different business type (not vehicle-based, or pricing that
doesn't vary by vehicle) needs real schema changes here, not just an env var or content
edit — this is the boundary of "reskin" vs. "new template type."

Given that, for future template types: not every current page will make sense, and new
ones will need to be built. The implementor for a given business picks which pages apply
and builds new ones that reference the domain concepts that actual business needs
(its own equivalent of `ServiceType`/`VehicleCategory`, or none at all).

## 7. Suggested next step (not done yet): isolate vehicle selection, not the whole page

Not executed as part of this pass — a concrete recommendation for when a second template
type actually gets built, not a route-level split. On closer look, `/scheduling` itself
is mostly generic: service selection, description, and pricing apply to any
appointment-based business. The only genuinely auto-specific piece is the year/make/model
picker backed by `VehicleSpec`/`VehicleCategory`/`vehicle-data`.

Direction: rename the underlying domain concept from "vehicle" to something generic (what
the service is being performed *on/for* — naming TBD when this is actually done), and
extract the year/make/model picker itself into a dedicated Svelte component with a
well-defined props/events contract (selecting one of these "subjects" and producing
whatever classification drives per-category pricing). A different template type would
implement its own component against that same contract (e.g. something other than
year/make/model) and swap it in — a one-line import change in `scheduling/+page.svelte`,
not a runtime plugin system — while the surrounding service/price/date-time flow stays
completely untouched.

`/portfolio`, `/reviews`, `/profile`, `/login`, `/create-account`, and the `/admin`
auth-gating layout are already business-type-agnostic and need no changes for this.

## 8. Per-deployment setup outside this repo

Not a code change, but needed for a real new client launch: a separate AWS Amplify app
(new Cognito User Pool, DynamoDB tables), a domain verified with the email provider
(Resend/SES) for the new `EMAIL_FROM_ADDRESS`/`EMAIL_CONFIRMATION_FROM_ADDRESS`, and the
client's own custom domain pointed at the new deployment.
